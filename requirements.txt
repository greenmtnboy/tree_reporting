# pytrilogy <=0.3.276 capped duckdb<1.5.0; 0.3.279 lifted that cap, so the
# duckdb>=1.5.3 pin below now resolves cleanly. Keep this floor at or above the
# cap-lifting release so a fresh `pip install -r requirements.txt` cannot
# silently resolve back to a duckdb<1.5.0 pytrilogy.
#
# Raised to 0.3.305, the first version verified to build the cross-city rollups.
# An older release generated SQL that bound a city's freshness column to the CTE
# reading that city's Parquet, while building that CTE's select list with only
# the row columns:
#   Binder Error: Values list "cheerful" does not have a column named
#                 "arbue_landmark_data_updated_through"
#   Binder Error: Values list "rambunctious" does not have a column named "tree_id"
# Both `landmark_info` and `tree_info` hit it; per-city Parquets were unaffected,
# so it only showed up when full_*_info was rebuilt. If those reappear, check the
# installed version first — the models are fine.
#
# Raised to 0.3.360, the first release that plans a lookup keyed on a derived
# concept across a partitioned union. raw/tree_position.preql derives
# `snap_cell` from each row's coordinates and joins the Overture lookup on it;
# on 0.3.359 and earlier that raised "Could not resolve connections" against
# the municipal/community/OSM partitions every city model is built from.
#
# Raised to 0.3.378: 0.3.377 computed the shared merge's cluster aggregates
# over the pruned rows and silently dropped trees, and usbos's border gate
# needs the planner fixes in 0.3.377/0.3.378. See docs/BORDER_DEDUP.md.
#
# Raised to 0.3.389: every city model extends the `template datasource`s in
# data/raw/tree_dedup.preql and landmark_common.preql, and published targets
# carry `assert` guards (core.preql); both parse from 0.3.389, and 0.3.391 is
# the first that can check a guard on a partial target (scoped to its
# `complete where`) instead of failing every city's `source_kept`.
#
# Raised to 0.3.414: the browser projection (data/raw/tree_browser_city.preql)
# declares a datasource `order by` and `storage (row_group_size = n)`, and
# sorts by `@hilbert_index` from std.geography; all three first ship there.
# Raised again to 0.3.419: 0.3.414 cannot plan that sort for a target with
# stored derived columns (pytrilogy #783, released in 0.3.417), and 0.3.417
# and 0.3.418 cannot plan any city's tree_info build (#786, fixed in 0.3.419).
pytrilogy>=0.3.419
# DuckDB 1.5.3+ is the first 1.5.x with the `nanoarrow` community extension
# published for linux_amd64 (1.5.0 ships `arrow` but not `nanoarrow`, so
# `LOAD arrow` fails with "Nested load of nanoarrow failed" on the runner).
duckdb>=1.5.3
